# Project Aurora

A modular runtime platform for iOS and iPadOS: one app that hosts many game
engines and console emulators behind a single, versioned module contract.

Status: **architecture prototype**, not a product. What works today is the
platform half - module registry, manifest validation, state machine, lifecycle
supervisor, storage isolation and a fault-injection test suite - plus a headless
host that runs it without any Apple framework. The iOS shell and the first real
emulator modules come next.

## Why it looks like this

Three constraints shaped everything here:

1. **iOS cannot load native code it downloads.** So "plugin" means *compiled into
   the app, registered at runtime*. The module table is generated by the build,
   not discovered from a folder.
2. **A missing or broken module must not matter.** A manifest without a binary is
   reported as DISCOVERED, an enabled module whose dependency is off is reported
   as BUILT with the reason, and a module that fails initialization is marked
   FAILED while everything else keeps running.
3. **A manifest is a claim, not proof.** READY comes from three inputs: the
   manifest, the generated build table, and the runtime probe. A manifest saying
   "status": "ready" changes nothing.

## Layout

    SDK/AuroraRuntimeAPI      the C ABI: one header, no C++ types across the boundary
    SDK/AuroraModuleSDK       manifest parsing, registry, state machine, host, supervisor
    SDK/AuroraStorageAPI      per-module storage isolation
    SDK/AuroraDiagnosticsAPI  log ring buffer and formatting
    Modules/                  one CMake target per module, one manifest each
    ModuleManifests/          the declarative half of each module
    Applications/Aurora-CLI   headless platform host (this is what CI runs)
    Tests/                    host test suite: registry, lifecycle, faults, storage

## Build and test on any desktop

    cmake -S . -B build -G Ninja
    cmake --build build
    aurora_core_tests                    # or: ctest --test-dir build
    aurora-cli list
    aurora-cli run com.aurora.runtime.simulated --frames 120 --out frame.ppm

No Apple SDK needed for any of the above. That is the point: the platform layer is
host-testable, so module-independent behaviour is proven before it reaches a
device.

## Module contract in one paragraph

A module exports one symbol, returns a vtable, and receives an AuroraHostServices
table at instance creation. It never calls the platform directly, never touches
another module, and cannot name a path outside its own storage tree. Everything it
returns is an AuroraStatus; nothing may throw across the boundary - and the
supervisor catches it if it does.

## Honest limits

- Modules share the app process. A SIGSEGV in a native module still kills Aurora.
  The fault-isolation spec documents this instead of pretending otherwise.
- App Store builds cannot download emulator code. Updates ship through app
  updates.
- JIT availability is a runtime property, not a distribution-channel property.
