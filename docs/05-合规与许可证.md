# 05 合规与许可证

对应任务书交付物 11、12。这一份不是法律意见，是把技术事实摆清楚，好做产品决策。

## 1. 现在的许可证事实

| 组件 | 许可证 | 来源 | 对整包的影响 |
|---|---|---|---|
| Project Aurora 自身代码 | 未定 | — | **待决策**，见第 4 节 |
| PPSSPP | GPL-2.0-or-later | 仓库 README（GitHub 识别为 NOASSERTION） | 静态链接后整包必须 GPLv2 兼容分发 |
| mGBA | MPL-2.0 | GitHub API 实测 | 文件级 copyleft，改动过的文件需开源，其余不受影响 |
| melonDS | GPL-3.0 | GitHub API 实测 | 整包必须 GPLv3 兼容分发 |
| DuckStation | 非 OSI 许可（CC BY-NC-ND 4.0） | 2024 年变更，媒体报道（网易/DoNews 等） | **不能与 App Store 商业分发共存**，且 ND 禁止修改后分发 |
| RetroArch / Libretro 核心 | GPL-3.0 | GitHub API 实测 | 同上 |

注意 GPLv2-or-later 与 GPLv3 的关系：GPLv2-**only** 的代码不能和 GPLv3 混，
但 PPSSPP 是 "or later"，所以能和 melonDS 一起放同一个 GPLv3 包里。

## 2. 直接后果

1. **一旦静态链接 PPSSPP，Aurora 整包按 GPL 分发**，源码必须公开，且必须提供对应源码。
   这与"闭源商业 App"不兼容。
2. **DuckStation 不能进首批**。要么拿到作者的另行授权，要么不接。这不是技术问题。
3. mGBA 是 MPL，可以整包 GPL 分发（MPL 与 GPL 兼容，MPL 代码保持 MPL）。

## 3. 与 App Store 的关系

- GPL 与 App Store 的冲突是长期问题（Apple 的分发条款附加限制与 GPL 的再分发自由冲突）。
  现实中有 GPL 软件上架，但存在法律不确定性，需要按项目定位选择策略。
- 更稳的做法是把 GPL 模块做成**独立的侧载包**，App Store 版本只带许可宽松的模块。
  这正好是架构上已经支持的能力：模块是构建期的，App Store 构建不链接 GPL 模块即可。
- 待核（需要原文核对，不是推断）：
  - App Store Review Guidelines 4.7 关于"小程序/插件/模拟器"的最新措辞
  - 2.5.2 关于"不得下载执行代码"的边界
  - 模拟器类 App 对 ROM 提供方式的具体要求

## 4. 需要产品决策的三件事

1. **Aurora 自身用什么许可证**：如果确定要接 GPL 模块，最省事的是从一开始就用 GPLv3；
   如果要做闭源商业版，就必须让 GPL 模块只出现在侧载包里，App Store 包不链接它们。
2. **App Store 版本带哪些模块**：建议只带 MPL/Apache/MIT 类模块。
3. **DuckStation 怎么处理**：不接 / 单独授权 / 换用别的 PS1 核心。

## 5. 其它合规项

- **BIOS/固件**：不随 App 分发，由用户提供。Manifest 里用 `requires_firmware` 声明，
  平台缺固件时把模块停在 BUILT 并提示。
- **游戏 ROM/资源**：不提供、不内置、不自动下载。平台只做本地文件导入。
- **字体与素材**：所有自带字体必须是可再分发的（OFL 等），不得从游戏里提取。
- **日志与遥测**：默认本地。要上传必须先有隐私政策与开关。

## 6. 当前状态

- 仓库暂未附 LICENSE 文件。**在许可证确定之前不要公开发布二进制产物。**
- 源码仓库已经公开（架构与文档），这不影响后续选择许可证，但一旦发布二进制就必须先定许可证。
