# 11 差异化：一个 App 里那些别人给不了的东西

现状：iOS 上同类的 Galgame / 模拟器应用不少（XP3Player 一类 krkr 播放器、各种单机模拟器、
RetroArch 这类前端）。它们大多长一个样：选文件 → 黑屏或闪退 → 用户自己猜哪里不对。

我们的差异化不该是"支持更多引擎"（那是堆人力），而应该是**别人架构上给不了的东西**。
下面三条都是从现有架构直接长出来的，不需要另起炉灶。

## 1. 统一游戏库 + 引擎自动识别

现状痛点：玩一个 krkr 游戏要开 A 应用，玩 PSP 要开 B 应用，存档分散在不同 App 里。

我们的做法：一个库，导入后自动判断它属于哪个引擎（xp3 归档 → krkr，nscript.dat → ONScripter，
iso/cso → PSP 模块，等等），再交给对应模块。

关键设计：**识别规则是数据，不是代码**。规则写在模块的 Manifest 里（文件名模式、归档魔数、
目录特征），平台只负责匹配。新增引擎时加一份规则即可，不改平台代码——这正是 13.5 验收所要求的。

## 2. 兼容性诊断：告诉用户"为什么不能跑"

现状：黑屏、闪退、卡在加载图，用户没有任何线索。

我们的做法：每次启动失败都来自状态机，能给出具体原因：

- 模块没编进这个版本 → "这个版本没带 PSP 模块"
- 缺固件 → "需要 BIOS 文件，放到 X"
- 格式不支持 → "这个文件不是该模块认的格式"
- 需要 JIT → "这个模块在没开 JIT 时只能慢速运行"
- 初始化失败 → "模块初始化失败，已记录日志，可重试"

这条是架构直接送的：三源可信度模型（Manifest + 构建表 + 运行时探测）本来就是为了区分
"没编进来"和"编进来了但跑不动"。竞品是硬编码引擎，做不到这种粒度。

## 3. 存档统一管理 + 永不误删

现状：换应用、删模块、重装，存档可能就没了；不同引擎的存档各管各的。

我们的做法：所有模块的存档都在平台统一目录下（RuntimeModules/<id>/Saves），
提供导出/导入、备份、版本迁移；删模块不删存档；重装覆盖安装存档保留。

## 4. 顺带的信任差异（不是主打，但真实）

- 全部源码 GPL-3.0 公开，构建可复现
- 本地优先：不联网、不上传游戏与存档
- 状态诚实：界面不把"还没验证"说成"已支持"

## 建议的主打

先打 **1 + 2**：统一游戏库 + 说得清失败原因。

理由：模块数量上我们短期赢不了任何一家；但"一个库管所有 + 出问题能看懂"
是用户第一天就能感受到的差别，而且它完全建立在我们已经验证过的架构上。

## 落地第一步

1. Manifest 增加 $detection$ 段（文件名模式 / 魔数 / 目录特征）
2. 平台加 Library 层：扫描导入目录 → 匹配模块 → 生成条目（记住来源与哈希）
3. 启动失败把状态机的 $unmet$ / $last_error$ 原样显示，不做美化
4. 真机验证：拿一个真实游戏目录，看识别与诊断是否说得准
