# 12 模块化能衍生出什么

模块化的价值不在于"能多接几个引擎"——那是体力活。真正的价值是：**把引擎变成可替换、
可观测、可回放的部件**。一旦引擎退化成部件，下面这些东西才有得谈。

每条都标了"机制从哪来"和"iOS 上的坑"。

## 1. 多实例：iPad 分屏同时跑两个游戏（强卖点）

**机制**：注册表按模块登记，运行态是"模块 + 实例"。实例本来就是一等的，
同时跑一个 ONScripter 和一个 krkr 不需要任何架构改动。

**用户感知**：iPad 分屏左边 Galgame、右边看图/攻略；或者一边挂机一边玩另一个。
竞品基本都是单实例。

**坑**：内存。两台引擎同时在跑，iPad 上要限制实例数（比如按设备内存给 1–2 个），
并在 UI 上明确"第二个实例可能被系统回收"。

## 2. 确定性重放：把"这游戏在某个地方必崩"变成可复现的输入序列

**机制**：ABI 里的 $tick(inst, dt)$ 是平台驱动的单步，输入是快照（$AuroraInputState$）。
记录每帧输入 → 重放 → 同样的崩溃/花屏能复现。

**用户感知**：报 bug 时可以附上"重放文件"，开发者不用猜；也可以做"倒带"（保留最近 N 帧状态）。

**坑**：前提是模块内部没有隐藏的时钟依赖（用宿主时钟，不用 $time(NULL)$）；
这一条要写进模块开发规范，且用测试卡住（拒绝非确定性模块的"重放"标签）。

## 3. 构建变体：一份代码出多个产品

**机制**：构建表由 $Modules/modules.list$ 生成，模块开关是 CMake 选项。
同一份源码可以出：完整版（全模块）、精简版（只有宽松许可模块）、
测试版（带故障注入模块）、真机调试版（带诊断日志）。

**用户感知**：不同发版渠道、不同合规定位的包，代码只有一份。

**坑**：无。这条现在就能用，只是还没做过第二个变体。

## 4. 模块级回滚与灰度

**机制**：模块版本与 App 版本独立；Manifest 记录上游 commit 与版本。
出问题时可以只回退某个模块，而不是回退整个 App。

**坑**：iOS 上模块是静态链接进 App 的，所以"回滚模块"实际是"发一个新 App 版本"。
这条能做的是**诊断层面的灰度**：同一 App 内保留模块 A 的两个实现（如果体积允许），
或通过远端开关切换默认模块（开关是数据，不是代码）。

## 5. 第三方模块开发套件（生态）

**机制**：现在已经有 SDK 头文件、模块模板、构建表生成、边界检查脚本
（$check_module_boundaries.py$ 保证模块只能 include 公共 ABI）、主机测试套件。

**衍生**：把这套东西整理成"30 分钟接一个新引擎"的模板 + 文档 + 检查清单。
别人能接引擎，平台就不再只靠我们自己堆模块。

**坑**：第三方模块的许可证必须过我们的准入闸（已有 $check_licenses.py$）。

## 6. 统一的"继续游戏"状态卡

**机制**：每个模块在 $query_status$ 之外，再导出一个"摘要"（当前存档号、截图、进度）。
平台把这些摘要统一渲染成首页的"继续游戏"卡片。

**用户感知**：不管玩的是 krkr 还是 PSP，回来一眼看到上次玩到哪。

**坑**：需要给 ABI 加一个可选的能力（次版本扩展即可），现在没有。

## 7. 帧级回归测试（工程侧特色）

**机制**：无头宿主 + 确定性 tick → CI 里跑真实游戏若干帧，把第 N 帧和基准图对比。
每个模块带自己的 golden 用例。

**用户感知**：看不到，但"这个版本把某个引擎搞坏了"能在合并前被发现。

**坑**：真机图形与主机软渲染结果可能有细微差异，基准图要按后端分档。

## 我建议先做的两个

1. **多实例（分屏）**：用户第一天就能感知，机制现成，主要是内存策略与 UI。
2. **确定性重放**：技术上现在就有基础（tick + 输入快照），做完能把"玄学 bug"变成可复现文件，
   也是第三方模块开发者最需要的东西。

构建变体与许可证准入闸已经在用，属于"顺手就有"，不用专门立项。
