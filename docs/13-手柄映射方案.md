# 13 手柄映射方案

调研结论：**这件事 Apple 已经把底座铺好了，我们缺的是"映射层"和"界面"，不是驱动。**

## 1. Apple 给的是什么

GameController 框架，官方支持 DualShock 4、DualSense、Switch Pro、Xbox 手柄，
并且提供 IMU、震动/触觉、自适应扳机。

- 设备模型：$GCController.controllers$ 拿当前设备，
  $GCControllerDidConnect$ / $GCControllerDidDisconnect$ 监听插拔
- 现代输入 API（iOS 16+）：$controller.input$ → $GCControllerLiveInput$，
  按语义名取元素（$GCInputButtonA$ 等），还能用 diff 只看变化的输入
- 旧一代：$GCPhysicalInputProfile$ 系列（Extended / Xbox / DualShock / DualSense）
- 震动：$GCController.haptics$ → $CHHapticEngine$
- IMU：$GCController.motion$

我们的最低版本正好是 iOS 16，可以直接用现代 API，不必迁就老 profile。

## 2. 我们已经有的

- $AuroraInputProfile$：JSON 描述 action → 手柄位/键码/触控区（C++ 已实现并测过）
- $applyProfile()$：把原始事件变成模块看到的 $AuroraInputState$
- $ModuleHost::setInput()$：把快照喂给正在跑的模块
- 存储布局里已有 $Shared/InputProfiles/$

也就是说：**数据模型和管线是现成的，缺的是"Swift 侧把 GCController 读出来"和"界面"**。

## 3. 要做的三层

1. **设备层（Swift）**：$GamepadManager$
   - 监听插拔，维护玩家 1/2 分配
   - 每帧从 $controller.input$ 采样：按钮位、左右轴、触发值
   - 投递到主线程，帧边界统一采样（不要在半帧中间读，避免撕裂）
   - 状态显示：手柄型号、电量、连接方式
2. **映射层（C++，已有 + 扩展）**
   - 现在支持 action → pad_mask / key_code / touch 区
   - 要补：摇杆→十字的方向锁定与死区、扳机→肩键阈值、曲线、连发
3. **界面层（SwiftUI）**
   - 按键学习：点界面上的键 → 按手柄上的键 → 存进 profile
   - 每个模块一套默认 profile，切换模块自动换
   - 实时预览：按手柄时界面高亮

## 4. 值得做的差异化

| 功能 | 说明 | 价值 |
|---|---|---|
| 按引擎预设 | ONS/krkr 只要 A/B/Start；PSP 要十字+摇杆+肩键 | 用户不用为每个引擎重配 |
| 摇杆转十字 | 死区 + 八方向锁定 | PSP 菜单、老游戏必须 |
| 自动连发 | RPG 刷素材 | 常见痛点 |
| 触屏↔手柄互映 | 实体键映射成触屏点，反之亦然 | 只支持触屏的老 Galgame 也能用手柄 |
| 按键提示层 | 按 X 时角标显示 "Xbox A / PS ×" | 不同手柄符号不同，Apple 的 API 能区分 |
| 震动 | 引擎的震动事件走 CHHapticEngine | 需要 ABI 1.2 加 vibrate 回调 |
| 多手柄分屏 | 配合我们的多实例 | iPad 上两人各玩一个 |

## 5. 坑

- **帧边界采样**：手柄回调线程与渲染循环不同步，必须在每帧开始时取一次快照
- **优先级**：iPad 上可能同时有触控、键盘、手柄；要有明确优先级（手柄 > 键盘 > 触控）
- **蓝牙延迟**：10–20 ms，别把它当成 bug 去"补偿"，只能如实呈现
- **App Store**：支持手柄就意味着 UI 必须可被手柄完整操作，HIG 有要求，审核会看
- **热插拔**：拔掉手柄时输入要归零，不能卡住最后按下的键

## 6. 落地顺序

1. $GamepadManager$ + 桥接 + 一个"连接状态"面板（能证明读得到）
2. 按键学习界面 + 每模块默认 profile + 存盘
3. 摇杆转十字、触发阈值、连发
4. 震动（需要 ABI 1.2）
5. 触屏互映与多手柄
