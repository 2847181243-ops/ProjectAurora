# 01 总体架构 · Aurora Modular Runtime Architecture

任务书 AURORA-ARCH-001 / Phase 1 交付物 01、02、03。
本文件描述的每一个接口、目录、状态都对应仓库里的真实代码；写进文档而代码里没有的，会在这里标出来。

---

## 1. 先说约束

架构不是风格选择，是这些条件推出来的。

### 1.1 iOS 不能加载下载来的原生代码

App Store 版不允许运行从网络下载的可执行代码，JIT 也受限。所以"插件化"在 iOS 上只能是：
**构建期集成 + 运行期注册**。模块表由 CMake 在构建时生成，App 启动时把表交给注册表；
不存在的模块就是表里没有，不是"文件夹里没找到"。

这直接否掉了 DLL/dylib 式插件，也否掉了"用户在线安装模拟器"这种产品形态。

### 1.2 同进程没有进程级崩溃隔离

所有 C/C++ 模块和 SwiftUI 跑在同一个进程里。模块里一次野指针 SIGSEGV，整个 App 连同其它模块一起死。
可以做到的是：错误返回、异常边界、状态清理、失败标记、局部重试；做不到的是拦截段错误。

任务书第九节要求"不得将普通异常捕获描述为能够阻止所有原生崩溃"——本文按这条写。

### 1.3 GPL 会传染到整包

PPSSPP（GPL-2.0-or-later）、DuckStation、melonDS 都是 GPL 系。静态链接进同一个可执行文件，
整包按 GPL 分发。mGBA 是 MPL-2.0，条款不同。

这不是"注意一下"的事：它决定了 App Store 是否可以上架、源码是否必须公开、以及侧载版的许可怎么写。
许可证矩阵单独放在 05 号文档，这里只记结论：**模块的许可证必须进 Manifest，且平台启动时能列出整包许可证集合。**

### 1.4 没有 Mac 在环

开发机是 Windows。CI 用 macOS runner 出未签名 ipa，签名与安装回到 Windows 侧完成。
因此平台层必须能在无 Apple 框架的机器上编译并跑测试——这不是妥协，是这套架构成立的前提。

## 2. 三层 + 适配器

`
Aurora App (SwiftUI, iOS/iPadOS)
        |
        v  只调用 SDK，不认识任何模拟器
Aurora Module SDK  ── Registry / Manifest / Lifecycle / Storage / Input / Display / Audio / Diagnostics
        |
        v  唯一的 C ABI
Runtime Modules    ── Empty / Simulated / FaultInjector / (future) PPSSPP ...
        |
        (适配器层在模块内部或模块与核心之间，用来吸收引擎差异：Native / Libretro / VisualNovel / Web)
`

三层之间的依赖是单向的：App → SDK → Module。反向没有任何一条路径——没有回调进 App 的函数指针，
没有全局单例，没有"模块自己去找游戏库"的入口。模块能碰到的一切，都在
`AuroraHostServices` 那张表里，由平台在创建实例时递过去。

**适配器不是第四层。** 它属于模块侧：一个 libretro core 的适配器是模块自己的事，
平台只知道"这个模块支持哪些格式、要什么能力"。把适配器做成平台的公共层，
等于让平台开始理解引擎差异，那是任务书 2.1 明确禁止的。

---

## 3. 依赖方向（可检查）

| 允许 | 禁止 |
|---|---|
| App → SDK | App → 模块内部实现 |
| SDK → 模块（通过 vtable） | 模块 → 模块 |
| 模块 → HostServices | 模块 → 平台内部符号 |
| 模块 → 自己的存储桶 | 模块 → 别的模块的存储桶 |
| 测试 → SDK + 模块 | 模块 → 任何 SDK 内部头文件 |

最后一条已经在构建里执行：`aurora_add_module()` 只给模块公开 ABI 头文件的 include 路径，
模块写 `#include "aurora/registry.h"` 直接编不过。

## 4. 核心契约（对应 SDK/AuroraRuntimeAPI/include/aurora/module_api.h）

### 4.1 模块侧

`c
typedef struct AuroraModuleVTable {
    uint32_t struct_size;      // 前向兼容：加字段不改老模块
    uint32_t abi_major;        // 主版本不同直接拒绝
    const char* module_id;     // 必须与 Manifest 一致
    AuroraStatus (*create_instance)(const AuroraHostServices*, void**);
    AuroraStatus (*load_game)(void*, const AuroraGameInfo*);
    AuroraStatus (*start)(void*);
    AuroraStatus (*pause)(void*);
    AuroraStatus (*resume)(void*);
    AuroraStatus (*stop)(void*);
    AuroraStatus (*query_status)(void*, AuroraModuleInstanceStatus*);
    void         (*release_instance)(void*);
    AuroraStatus (*tick)(void*, double);   // 可选：平台驱动的确定性单步
} AuroraModuleVTable;
`

纯 C，没有 C++ 类型穿过边界。每个模块只导出一个符号，名字带模块后缀
（`aurora_module_entry_ppsspp`），两个静态库同时链接不会撞名。

`tick` 是给测试和无头采集用的：有它就能一步步推进、断言第 N 帧的内容；
没有它就说明模块自己带循环，平台只负责 start/stop。

### 4.2 平台侧

`c
typedef struct AuroraHostServices {
    uint32_t struct_size; void* host_context;
    AuroraStatus (*storage_directory)(void*, const char* module_id, AuroraStorageKind,
                                      const char* relative, char* out, size_t cap);
    void         (*write_log)(void*, const char* module_id, AuroraLogLevel, const char*);
    AuroraStatus (*acquire_frame)(void*, uint32_t w, uint32_t h, AuroraFrame*);
    AuroraStatus (*present_frame)(void*, const AuroraFrame*);
    AuroraStatus (*poll_input)(void*, AuroraInputState*);
    double       (*monotonic_seconds)(void*);
} AuroraHostServices;
`

关键点：`host_context` 指向的是**这个模块自己的绑定**，不是全局宿主。
绑定里记着模块 id、自己的画面缓冲、自己的输入快照。模块拿着别的模块 id 来要目录，
回调当场拒绝并记一条违规，而不是"文档里写了不许"。

## 5. 可信度模型：三个来源，缺一不可

任务书第五节要求"Manifest 里的 status 不能当作模块可用"。落到实现上：

| 来源 | 回答的问题 | 谁产生 |
|---|---|---|
| Manifest | 它声称自己是什么 | 模块作者，随仓库提交 |
| 构建表 | 这次构建到底编进了什么 | CMake 生成，随二进制走 |
| 运行时探测 | 创建实例成功没有 | 平台启动时真实调用 |

三者合一才得到状态。具体规则：

- 有 Manifest、构建表里没有 → DISCOVERED（"未编入本版本"）
- 构建表里有、Manifest 没有 → FAILED（构建表和仓库不一致，属于构建缺陷）
- Manifest 非法 → FAILED，并把逐字段错误挂上去
- Manifest 写 `status: ready` 但二进制缺失 → 仍然是 DISCOVERED。这一条有专门的单元测试
  （`registry_ignores_a_claimed_ready_status`）。

## 6. 状态机

`
DISCOVERED ──→ BUILT ──→ READY ──→ RUNNING
     │           │  ↑        │  ↑       │
     │           │  └────────┘  └───────┘
     │           ↓
     └────────→ DISABLED ←── FAILED
`

- `DISCOVERED`：有声明，没有可用二进制
- `BUILT`：编进来了，但启动条件没齐（SDK 不兼容、依赖没就绪、缺固件、被禁用以外的前置条件未满足）
- `READY`：前置条件全齐，能起游戏
- `RUNNING`：实例活着
- `DISABLED`：用户关掉，数据保留
- `FAILED`：探测或运行失败

状态迁移只在 `state_machine.cpp` 的边表里允许，别的一律拒绝并记录。
派生状态要重算时走最短合法路径（`transitionPath()`），不是直接赋值。

**失败是粘滞的。** 一个模块初始化失败后，即使所有前置条件后来都满足，也停在 FAILED，
直到用户点"重试"（`resetFailure()`）。否则每次重算都把它算回 READY，
等于把崩溃藏起来。

`PLANNED` / `BUILDING` 是构建期状态，运行中的 App 不会产生它们，定义在同一个枚举里只是为了 UI 和构建报告用一套词。

## 7. 生命周期与失败语义

`
start():  find → 状态必须 READY → createBinding → create_instance → load_game → start → RUNNING
tick():   实例必须 RUNNING → 模块 tick → 刷新状态
stop():   stop → release_instance → 释放绑定 → RUNNING→READY
`

失败分两类，这个区分来自真实场景，不是形式主义：

| 分类 | 错误码 | 处理 |
|---|---|---|
| 用户错误（可重试） | UNSUPPORTED_GAME、MISSING_FIRMWARE、IO、CANCELLED | 拆掉实例，模块回到 READY，用户可以换个游戏再来 |
| 模块缺陷（需重置） | INIT_FAILED、INTERNAL、ABI_MISMATCH、OUT_OF_MEMORY | 拆掉实例，模块置 FAILED，保留存档，等重试 |

异常边界：所有跨 ABI 调用都包在 `try/catch(...)` 里。模块承诺不抛，但承诺不算证据——
`fault_exception_across_the_abi_is_caught` 用故意抛异常的模块验证平台不会跟着炸。

## 8. 存储隔离

`
AuroraData/
  RuntimeModules/<module_id>/{Config,Saves,States,Logs}
  Shared/{InputProfiles,DisplayProfiles,Backup}
  Diagnostics/{CrashReports,RuntimeLogs}
`

规则由 `StorageLayout` 实现，不是靠约定：

1. module_id 必须是 `[a-z][a-z0-9_.]*`，不能含 `..`
2. 相对路径不能是绝对路径、不能有盘符、不能含反斜杠、不能有 `..` 段
3. 解析完再做一次前缀校验，防止绕过
4. 平台负责建目录，模块只拿路径

删除模块只删二进制和 Manifest 条目，不删 `RuntimeModules/<id>`。
用户存档和游戏原文件分开存放，这是任务书第八节第 7 条。

## 9. 故障边界（诚实版）

**能做到：**

- 模块返回错误 → 记录、拆实例、置 FAILED、其它模块继续
- 模块抛 C++ 异常 → 在边界捕获，按 INTERNAL 处理
- 模块越权访问别人目录 → 回调拒绝并留证据
- 模块卡死 → 目前只有协作式超时，没有抢占式看门狗（见未决问题）
- 崩溃后重启 → 平台重新注册，FAILED 模块可以被重试

**做不到：**

- 段错误（SIGSEGV）、栈溢出、堆破坏 → 进程直接死
- 死锁 → 平台一起卡住

如果之后要真隔离，只有两条路：XPC/独立进程（iOS 上受限且开销大），
或者把高风险模块放进受限子进程 + 共享内存传帧。两者都是后续架构变更 Issue 的题材。

## 11. 关键决策

| 决策 | 选择 | 理由 | 被否掉的替代 |
|---|---|---|---|
| 模块边界 | 纯 C ABI vtable | Swift 桥接简单、无 C++ ABI 依赖、可被任何语言实现 | C++ 虚基类（跨编译器不稳）、Swift protocol（C++ 模块接不进来） |
| 模块发现 | 构建期生成表 | iOS 不允许运行期加载；缺失模块天然就是"表里没有" | 目录扫描、dylib dlopen |
| 清单格式 | JSON + 手写解析器 | 不引入第三方 JSON 库，减少许可证面；解析器 300 行可控 | nlohmann/json（头文件巨大、许可证虽可用但没必要） |
| 状态来源 | Manifest + 构建表 + 探测 | Manifest 会撒谎，构建表不会 | 只信 Manifest |
| 失败处理 | 粘滞 FAILED + 显式重试 | 避免重算把崩溃洗掉 | 自动重算 |
| 存储 | 平台解析路径 | 模块拿不到越权路径 | 给模块一个 root 让它自己拼 |

## 12. 未决问题

1. **看门狗。** 模块 tick 卡住怎么办？现在只能靠模块自觉。候选方案：平台侧计时 + 强制 stop，
   但同进程里"强制"也只是发个标志位。
2. **帧传输。** 现在是模块直接写平台给的 RGBA 缓冲。接 Metal 时要决定是 CPU 拷贝还是共享纹理，
   以及垂直同步由谁负责。
3. **音频。** ABI 里只有 host 侧日志和画面，音频接口还没定义。接入第一个真引擎前必须补。
4. **App Store 合规。** 任务书 4.7 / 2.5.2 的最新措辞需要原文核对，见 05 号文档。
5. **许可证传染。** GPL 模块进同一二进制后，平台层和 SDK 必须以 GPL 兼容条款发布。
   是否接受，需要产品决策，不是技术决策。
